视频能播出来，只说明链路通了。对实时操作来说，更关键的是屏幕上的画面离现在有多远：网络已经恢复，播放器却还在消化旧数据，这时“连接正常”并不能说明系统已经恢复。

我想把 RTSP 延迟拆成两条线来看。一条是正常运行时，时间花在接收、解码还是排队；另一条是连接出错之后，系统怎样回到一张真正属于新会话的画面。前者决定缓冲怎么设，后者决定状态机怎么写。

## 1. 先建立端到端预算

```text
采集 → 编码 → 发送缓冲 → 网络 → 接收缓冲 → 解码 → 显示
                                                └─ AI 分析
```

端到端延迟是各阶段服务时间与等待时间的总和。吞吐量足够，也可能因为队列等待导致高延迟；反之，把所有缓冲压到最小，也可能使网络抖动直接变成卡顿。

跨设备时间戳只有在时钟可比较时才能直接相减。一个简单的外部验证方式是拍摄可见计时器，并在接收端记录显示结果。它包含采集和显示延迟，但分辨率受相机帧率、显示刷新和测量方法限制。

系统内部再记录接收、解码完成和渲染提交时间，就能进一步区分问题发生在哪段。只测 `decode()` 的耗时，不是测端到端延迟。

## 2. TCP 与 UDP 是不同的失败行为

RTSP 会话管理和媒体数据传输不是同一个层次。FFmpeg 支持通过 TCP 交织传输媒体数据，也提供 UDP 等传输选项；具体选项见 [官方 RTSP 文档](https://ffmpeg.org/ffmpeg-protocols.html#rtsp)。

TCP 的可靠有序交付会在丢包后等待重传；UDP 不提供相同的传输保证，需要上层处理丢失和乱序。不能因此推出“UDP 永远更快”或“TCP 永远更稳定”。实际体验还受编码结构、网络策略、接收缓存和解码恢复能力影响。

下面的命令只用于比较传输条件下的接收与解码日志，不测量屏幕显示延迟：

```bash
ffmpeg -hide_banner -loglevel info -rtsp_transport tcp \
  -i rtsp://camera.example/live -t 30 -an -f null -
```

将传输方式替换为 `udp` 后，在同一输入条件下比较错误、输出速度与恢复行为。地址为占位示例，实际使用时应记录 FFmpeg 版本，并确认设备支持相应传输方式。

## 3. 缓冲是预算，丢帧有位置

对实时预览，丢弃过期的已解码图像通常比持续展示旧画面合理。但压缩视频中的帧可能存在参考依赖，不能把任意压缩包当作独立图片丢弃。

| 丢弃位置 | 可能收益 | 需要考虑的代价 |
|---|---|---|
| 推理队列 | 保持分析结果较新 | 可能漏掉短事件 |
| 已解码展示队列 | 减少显示积压 | 运动不连续 |
| 压缩数据队列 | 降低后续处理负载 | 参考链受损，需等待恢复点 |

首先应限制队列容量并观察等待时间。如果输入长期超过处理能力，有界队列只能控制积压，不能增加算力。此时要减少输入分辨率、通道数或处理频率。

还要明确录像与操作预览是否共用同一丢弃策略。预览优先新鲜度，录像通常优先完整性，两者应分别设计。

## 4. 重连成功不等于恢复成功

可以用以下状态区分“网络已连接”和“业务已恢复”：

```text
DISCONNECTED → CONNECTING → WAITING_FOR_FRAME → STREAMING
                    失败 / 超时 ↓                  ↓ 停滞
                            BACKOFF ←───────────────┘
```

进入 `STREAMING` 的条件应包括收到并解码出有效的新会话画面，而不是仅成功打开套接字。为连接建立、首帧等待和运行中停滞分别配置超时，故障日志也分别记录。

重试采用有上限的退避并加入抖动，避免多通道同时反复连接。成功恢复之后再重置退避；认证失败、地址错误等配置问题则不能无限重试掩盖。

每次新连接分配新会话编号，旧解码器和推理任务的结果不能继续更新新会话界面。清空的是应用持有的过期状态，而不是假设网络恢复后所有历史数据自动消失。

## 5. 如何设计一组有解释力的实验

先固定分辨率、码率、编码参数和设备版本，再单独改变网络条件。测试应包含稳定网络、短时断网、持续限速和间歇丢包。

每组至少记录画面年龄分布、首帧时间、断网到有效画面恢复的时间、失败次数以及 CPU 使用。必须同时报告恢复失败的样本，不能只统计成功重连后的平均耗时。

如果修改缓冲配置后延迟下降但卡顿增多，这是取舍，不应只报告前一项。最终预算应由使用场景决定：远程操作、现场巡检和历史回放，对实时性的要求并不相同。

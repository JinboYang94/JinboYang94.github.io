我看 Agent 的执行流程时，最在意的是工具返回之前的那段空白。模型决定了下一步，系统也发出了请求，但如果响应一直没有回来，这一步到底算没做，还是已经做完了？

设想一个资源预订任务：请求发出十秒后超时。如果服务端已经完成预订，只是响应丢失，重试可能再订一次；如果服务端根本没有执行，跳过又会留下一个未完成的任务。同一句“工具调用失败”，背后其实是两种完全不同的世界状态。

所以我想讨论的恢复，并不是把旧对话再发给模型。真正需要恢复的是执行进度，以及每一步所依据的证据。

## 1. 把对话历史与任务状态分开

对话可以保存推理上下文，却不适合作为执行状态的唯一来源。恢复过程需要能够确定哪些信息仍有效，哪些步骤已经提交，哪些结果需要查询。

我会先把需要恢复的信息写成一份显式状态。下面这份 JSON 只保留当前例子需要的字段：

```json
{
  "task_id": "demo-task",
  "revision": 7,
  "goal": "reserve_resource",
  "constraints": {"resource": "machine-A", "slot": "demo-slot"},
  "step": "reservation",
  "operation_key": "demo-task:reservation:1",
  "status": "outcome_unknown",
  "evidence": {"source": "reservation_service", "version": 12}
}
```

字段的关键在于可检查的语义：`revision` 用于识别状态版本，`operation_key` 标识一次逻辑操作，`outcome_unknown` 则区分“确定失败”和“无法确定结果”。

这些信息仍然需要业务系统验证。把旧观测写进结构化 JSON，不会自动让它变成真实的当前状态。

## 2. 超时不是撤销

工具返回可以至少分为三类：确定成功、确定失败、结果未知。只有在失败原因与操作语义允许时，重试才是合理动作。

```text
准备操作 → 记录操作意图 → 调用工具
                           ├─ 成功 → 验证结果 → 提交状态
                           ├─ 明确拒绝 → 修正计划或结束
                           └─ 超时 → 查询操作状态 → 再决定是否重试
```

客户端取消等待，不保证服务端任务停止。Python 的异步取消也涉及协程响应取消与清理过程，不能把本地任务取消当成远端副作用撤销；相关行为见 [asyncio 任务文档](https://docs.python.org/3/library/asyncio-task.html)。

如果外部服务支持幂等键，重复提交同一逻辑操作时应复用原键，而不是每次重试都生成新键。若服务不支持幂等或状态查询，就需要额外的去重机制，或者将未知结果交给人工处理。

## 3. 检查点与事件日志解决不同问题

检查点给出某一时刻的状态快照；事件日志记录状态为何变化。二者配合，才能在恢复时解释操作顺序。

| 记录 | 作用 | 关键字段 |
|---|---|---|
| 操作意图 | 在发起副作用前留下证据 | 操作键、参数摘要、状态版本 |
| 工具结果 | 记录实际观测 | 结果状态、来源、时间与服务版本 |
| 验证结果 | 判断目标和约束是否满足 | 验证器版本、依据、失败原因 |
| 状态提交 | 推进流程 | 新版本、关联事件、下一步 |

“记录成功之后再更新状态”仍可能在两步之间崩溃；“先更新状态再记录”也存在相反窗口。实际实现应尽量将本地事件与状态更新放在同一事务中，并通过操作键处理跨系统边界。

对于并发执行，还需要版本比较或其他并发控制。否则两个工作者可能从同一个检查点恢复，并重复执行同一步骤。

## 4. 回放时默认重用证据，而不是重复副作用

日志回放至少有两种不同含义。诊断回放使用已记录的工具响应，分析 Agent 当时为何采取某个动作；执行恢复则可能继续与真实环境交互，必须重新确认外部状态。

把“回放”实现为从头重新调用所有工具，对查询工具和写操作具有完全不同的风险。资源预订、发送通知、提交工单等操作都不能无条件再次执行。

因此，应给工具标注读写语义，并把已完成副作用与可重算步骤分开。恢复时先核对前置条件、证据有效期和操作状态，再决定沿用结果、重新查询、补偿还是人工接管。

## 5. 可靠性需要故障注入来证明

最有价值的测试点往往位于边界：请求发出前崩溃、服务已执行但响应丢失、本地收到结果却尚未持久化、业务约束在恢复前发生变化。

对每个故障点，都检查几个不变量：

- 同一逻辑操作不会产生未经允许的重复副作用。
- 过期证据不会直接授权后续动作。
- 任务不能仅凭模型声称成功就结束。
- 无法消除的不确定状态会被显式保留。

统计时同时报告完成率、重复操作率、恢复时间和人工介入比例。只报告工具调用成功率，可能掩盖任务完成了但违反业务约束的情况。

独立验证也要有明确边界：用同一个模型再问一句“你确定吗”，不等于获得了独立证据。更有用的是查询实际业务结果、执行确定性检查，或由独立来源核对约束。

回到那个超时的预订请求，我希望恢复后的系统能回答：这次请求用了哪个操作键，服务端有没有留下记录，下一步需要查询还是重试。能回答这几个问题，对我来说比让模型重新生成一份完整计划更接近“从中断处继续执行”。

我更愿意把 Text-to-CAD 看成一个程序生成问题。输入是一段不完全精确的自然语言，输出是一组可以执行的建模操作。几何形状是执行结果，而用户真正希望留下的，往往还包括尺寸之间的关系，以及下一次修改时应该保持的约束。

单轮生成容易掩盖这一点。两段程序可以画出同一块板，第二轮只说一句“把板加长”，它们却可能产生不同的结果。我想从这个小例子展开，看看问题究竟出在语言理解、代码生成，还是程序本身的表示上。

## 1. 相同的几何可以来自不同的程序

设一块板长 80、宽 40、厚 6，左右各有一个孔，孔中心距离对应端面 10。以板中心为原点，两个孔的横坐标是 -30 和 30。

只看这一次输出，下面两种写法没有差别：

```python
# 写法 A：保留当前坐标
hole_x = [-30, 30]

# 写法 B：保留坐标与尺寸的关系
length = 80
edge_offset = 10
hole_x = [-(length / 2 - edge_offset), length / 2 - edge_offset]
```

现在把板长改成 100。写法 A 中孔的位置不变，写法 B 中孔会移动到 -40 和 40。哪一个正确，取决于最初的需求是在固定坐标，还是在固定边距。

这个例子让我觉得，渲染相似度只能评价某一次执行的结果。它无法单独判断程序有没有保留设计关系，更不能替下一轮编辑作保证。对于交互式生成，我希望模型留下的状态能够解释“这些数字为什么是这样”。

## 2. 把语言到程序的过程拆开

如果直接让 LLM 输出完整脚本，歧义处理、对象定位和 API 调用都挤在同一次生成里。脚本出错后，很难判断应该修哪一层。

我会先考虑下面这条处理路径：

```text
自然语言需求
    ↓
对象、参数、关系及尚未确定的假设
    ↓
带稳定标识的中间表示
    ↓
依赖检查与代码生成
    ↓
隔离执行 → 几何检查 → 反馈到对应节点
```

这里的中间表示有点像编译器里的 IR，但前端输入比源代码含糊得多。例如“把孔移近一点”没有给出距离，“左侧”也依赖观察方向。这样的信息应该保留为待确认项或显式假设，而不是悄悄变成一个数字。

为了把问题限制在参数依赖上，我先假定单位都是毫米，板的局部坐标系已经确定。一个简化的表达可以写成：

```json
{
  "units": "mm",
  "parameters": {"length": 80, "width": 40, "thickness": 6,
                 "hole_radius": 3, "edge_offset": 10},
  "features": [
    {"id": "plate", "kind": "box"},
    {"id": "left_hole", "kind": "through_hole", "parent": "plate",
     "x": {"op": "neg", "arg": "half_span"}},
    {"id": "right_hole", "kind": "through_hole", "parent": "plate",
     "x": {"ref": "half_span"}}
  ],
  "bindings": {
    "half_span": {"op": "sub",
                  "args": [{"op": "div", "args": [{"ref": "length"}, 2]},
                           {"ref": "edge_offset"}]}
  }
}
```

这只是本文约定的结构，不是一种现成标准。它有意保留了对象 ID 和表达式树：前者用于定位，后者用于追踪参数变化。实现时可以只允许有限的运算符，在求值前检查引用、单位和循环依赖，不需要把模型生成的表达式直接交给 `eval`。

稳定 ID 也不等于稳定的几何索引。一次布尔操作之后，几何内核给出的面顺序可能变化；语义节点与最终实体之间还需要维护对应关系。否则模型虽然找到了 `left_hole`，执行层仍可能改错对象。

## 3. 一次编辑实际上是在传播依赖

对于“把两个孔移近边缘 2 毫米”，上面的表示只需要把 `edge_offset` 从 10 改为 8，再重新计算依赖它的节点。

```text
edge_offset
    ↓
half_span
    ├─ left_hole.x
    └─ right_hole.x
```

如果指令变成“只移动左孔”，问题就不同了。修改共享边距会连带改变右孔；要实现局部编辑，必须把左孔的位置关系单独表示，并说明对称约束是否被解除。

我关心的最小修改因此不是字符数最少的 diff，而是语义上最小的影响范围。重写一段脚本可能碰巧保住所有约束，只改一个数字也可能破坏原本正确的关系。

在实现上，我会先让模型提出结构化编辑，再由程序检查目标节点、可写字段和依赖范围。检查通过后生成候选版本，执行和验证也针对这份候选版本；只有全部通过，才替换当前有效状态。失败时保留原版本和错误信息，下一轮修复就有明确起点。

## 4. 从中间表示到可执行程序

对于这个简单例子，后端可以是 CadQuery，也可以是其他支持参数化操作的接口。以 CadQuery 的工作平面与打孔接口为例，参数计算和建模操作可以分开写：[官方入门文档](https://cadquery.readthedocs.io/en/latest/quickstart.html)。

```python
import cadquery as cq

length, width, thickness = 80.0, 40.0, 6.0
edge_offset, radius = 10.0, 3.0
assert length > 0 and width > 0 and thickness > 0
assert radius > 0
assert radius < edge_offset < length / 2 - radius
assert radius < width / 2

half_span = length / 2 - edge_offset
centers = [(-half_span, 0), (half_span, 0)]
plate = (
    cq.Workplane("XY")
    .box(length, width, thickness)
    .faces(">Z").workplane()
    .pushPoints(centers)
    .hole(2 * radius)
)
```

这段代码只表达当前例子的两孔板。前置条件保证孔与板边、两个孔之间留有间隔，不覆盖任意零件的有效性。完整生成系统还需要在隔离进程中执行，限制时间和资源，并对返回实体做检查。

这里有一个值得比较的设计选择：让模型直接输出所有代码，还是让模型输出 IR，由确定性的后端生成代码？前者表达灵活，后者更容易约束操作范围和追踪错误。我倾向于先在有限的特征集合上验证后者，再看哪些表达确实需要开放给模型。

## 5. 反馈要能回到出错的那一层

“执行失败，请重新生成”把太多问题合并成了一句话。我希望反馈至少能区分以下几类：

| 失败位置 | 具体例子 | 修复需要知道什么 |
| --- | --- | --- |
| 需求解析 | “移近一点”缺少距离 | 哪个字段待确认 |
| IR 检查 | 引用不存在的节点、依赖成环 | 节点 ID 与依赖路径 |
| 程序执行 | API 调用错误、执行超时 | 对应操作与异常位置 |
| 几何验证 | 孔越界、实体无效 | 违反的约束与相关参数 |
| 编辑验证 | 左孔改对了，右孔也被移动 | 目标变化与应保持不变的属性 |

反馈越接近错误发生的位置，修复越容易限定范围。比如右孔被意外移动，重新描述整块板不一定有帮助；指出“本次编辑只允许改变左孔，右孔横坐标发生了变化”，才给出了可验证的修复目标。

我也不想把验证器写成另一段笼统的模型判断。尺寸、引用和依赖能由程序检查，就先做确定性检查；需要视觉或语义判断的部分，再单独记录它们的不确定性。

## 6. 我会怎样判断它是否真的更可编辑

如果只比较初始生成成功率，中间表示的价值很难体现。我会在初始结果正确的样本上继续发出编辑指令，分别记录目标是否改变、非目标属性是否保持，以及多轮修改后早先的约束是否仍成立。

数据划分也要围绕这个问题来做。同一个模板换几个尺寸就进入测试集，更多是在测试参数插值；按模板或结构族划分，才更接近测试新结构上的理解能力。两种设定都可以保留，但应该分别报告。

还有一个我会特别保留的对照：同样的语言模型和数据预算，一组直接生成脚本，另一组经过 IR。除了正确率，还记录每次修复的范围、执行次数和额外延迟。中间表示增加了一层系统复杂度，它是否值得，应由这些结果来回答。

回到“把板加长”这句话，我希望系统不只是给出一个更大的形状，还能沿着参数依赖说明哪些地方随之改变、哪些地方保持不动。这种可追踪的状态，是我理解 Text-to-CAD 与普通一次性代码生成差别的起点。

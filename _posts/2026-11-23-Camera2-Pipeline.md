看 Camera2 时，我会先画出图像的去向，而不是从 API 列表开始记。预览拿走一份数据，分析线程拿走另一份，页面退出时又要把这些路径收回来。只要其中一处没有交代清楚，问题就可能表现为预览停住、图像错位，或者退出后相机仍被占用。

把这条链路看成一个并发程序，我觉得最值得追的是三个问题：缓冲区现在属于谁，分析结果对应哪一帧，以及晚到的回调还有没有资格更新界面。下面按这个顺序整理。

## 1. 两条输出路径，不是一个串行回调

Camera2 通过捕获会话把图像送到配置的输出 Surface。应用可以将预览与图像分析组织为不同输出，但支持的尺寸、格式和输出组合取决于设备能力，必须查询并验证。接口关系见 [Camera2 官方概述](https://developer.android.com/media/camera/camera2)。

```text
CameraDevice → CaptureSession → 重复捕获请求
                              ├─ 预览 Surface → 显示
                              └─ ImageReader → 图像副本 → 分析线程
                                                    └─ 结果 → UI
```

两条路径让预览不必等待每次推理结束，但它们仍共享硬件资源。分析流分辨率过高、图像拷贝过多，仍可能拖慢系统。

因此先区分两个预算：预览需要的更新频率，以及分析结果允许的年龄。检测每秒执行几次应由任务需求决定，不必与相机帧率相等。

## 2. 最重要的约定是 Image 的所有权

`ImageReader` 提供的 `Image` 不是随意留存的普通数组。未关闭的图像会占用缓冲；达到上限后，获取新图像可能失败。实时处理常用 `acquireLatestImage()` 获取最新帧，但它正常丢弃旧帧也需要足够的可用缓冲空间，不能只把 `maxImages` 机械地设为 1。具体行为见 [ImageReader 文档](https://developer.android.com/reference/android/media/ImageReader)。

我倾向于先用复制方案把所有权分清：

```text
获取图像
  ├─ 没有图像：返回
  └─ 有图像：复制分析需要的数据
               ├─ 无论复制成功或失败，都关闭 Image
               └─ 成功后把独立副本交给分析线程
```

如果把 `Image` 直接交给后台任务，释放责任就必须一同转移。页面退出、队列替换、任务取消和推理异常，都要有释放路径。否则正常流程没有泄漏，并不能说明异常流程安全。

复制方案付出了内存带宽成本，但缩短了相机缓冲被占用的时间。缓冲池可以减少重复分配，不过归还时机仍必须晚于最后一个消费者完成读取。

## 3. YUV 到模型输入是一份数据协议

相机输出不能默认是紧密排列的 RGB。处理 YUV 图像时，需要尊重平面的行跨度与像素跨度，再明确转换、旋转、裁剪和缩放的顺序。

| 阶段 | 必须保存的信息 | 典型错误 |
|---|---|---|
| 获取 | 时间戳、原始尺寸、会话版本 | 结果无法对应输入帧 |
| 转换 | 格式、stride、颜色约定 | 色偏或图像错位 |
| 预处理 | 裁剪区域、旋转、缩放及补边 | 检测框整体偏移 |
| 展示 | 视图尺寸、镜像、缩放模式 | 框在不同方向下失准 |

以 letterbox 为例，模型坐标回到原图时，要先减去补边，再除以缩放比例。之后才能应用预览视图的变换。如果预览使用中心裁剪，不能只根据视图宽高做线性缩放。

排查时可以先不用模型，直接把原图四角和中心点映射到屏幕。五个点都不正确时，换检测模型不会解决问题。

## 4. 页面关闭是一次状态迁移

一个简化生命周期是：

```text
CLOSED → OPENING → CONFIGURING → RUNNING → CLOSING → CLOSED
                     └──────── 失败清理 ────────────┘
```

最容易漏掉的是关闭发生在异步打开过程中。用户已退出，但稍后到达的打开成功回调又启动了会话。可以为每次启用相机分配单调递增的会话版本；回调提交结果前核对版本，过期回调只清理资源。

关闭顺序应保证不再接收新任务，再停止捕获和关闭相关对象，并清理分析队列。不能在持有 UI 所需锁时同步等待分析线程结束，否则容易形成互相等待。

## 5. 用故障场景验证，而不仅是看预览是否出现

如果只验证“预览能出现”，我还不敢判断这条链路是否正确。我会固定设备和分辨率，把退出时机和处理速度作为变量：

- 连续打开和退出页面，观察相机与线程是否残留。
- 在打开、配置和推理期间分别退出，检查晚到回调。
- 人为放慢分析任务，观察待处理数据是否有界。
- 切换横竖屏，验证坐标、缓冲和会话状态。
- 模拟预处理异常，确认图像仍被释放。

每帧记录会话版本、获取时间、分析开始与结束时间，并区分“没有新帧”和“有帧但未展示”。这些证据比单个平均 FPS 更容易定位故障。

把这些路径画完整之后，Camera2 对我来说就不再是一组零散的回调：获取图像意味着接管一份资源，提交结果意味着确认一次会话，关闭页面意味着停止接受新的工作。再往下讨论吞吐量时，我会接着看 [多路视频管线]({% post_url 2026-11-20-Multi-Stream-Video-Pipeline %})。

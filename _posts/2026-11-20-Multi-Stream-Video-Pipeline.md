多路视频里有一种很容易误判的“慢”：画面还在更新，模型也在返回检测结果，但框已经跟不上眼前的人和物。只看 FPS，系统似乎还正常；把采集时间和展示时间放在一起，才会发现它正在稳定地处理过去。

我更关心这种延迟是怎样累积起来的。一个函数耗时变长，通常还能沿调用栈查下去；采集、解码、推理和显示各自跑得都不算慢，却可能因为队列和调度方式不同，拼成一条越来越落后的链路。

这篇笔记就从一条视频链路开始，逐步加上推理、多路输入和前端叠框。代码只保留讨论需要的部分，先把数据应该等待、被替换还是被拒收说清楚。

## 1. 共享资源，分开消费

```text
视频源 → 接收与解码 → 已解码帧
                        ├─ 预览路径：展示新画面
                        ├─ 推理路径：按预算选帧 → 输出识别结果
                        └─ 记录路径：按完整性要求独立处理

控制路径：通道配置、会话版本、启停状态、模型版本
观测路径：队列等待、帧年龄、错误事件、资源使用
```

预览、推理和记录对数据的要求不同。预览可以在过载时放弃旧画面，持续记录则可能要求完整保存；推理还可能依赖连续时序。不能用一个无界队列承担所有消费场景。

这里假设每路视频独立解码，推理由共享工作者处理。不同硬件实现可能采用批处理或专用执行器，但容量预算和数据身份的问题仍然存在。
## 2. 把处理时间与等待时间分开

每秒显示多少帧，只能反映画面更新的频率。如果系统稳定显示三秒前的内容，帧率再高，也不能满足实时观察的要求。

可以把一次展示的延迟拆成：

```text
采集 → 编码 → 网络传输 → 解码 → 等待处理 → 推理 → 渲染
                              └──────────→ 预览
```

这里有两个不同目标：预览希望及时显示画面；推理希望在有限计算资源内提供有用的识别结果。把二者串行绑定，意味着模型变慢时，整个预览也必须跟着变慢。

排查前先记录三类指标：

| 指标 | 回答的问题 |
|---|---|
| 各阶段耗时的中位数与高分位数 | 哪个环节慢，是否存在长尾？ |
| 排队数量与最老任务等待时间 | 系统是否正在积压？ |
| 展示帧与结果的时间差 | 画面与识别结果是否仍然匹配？ |

跨设备时间戳不能直接相减。端到端延迟需要时钟同步或其他可校准的测量方法；单进程内部的耗时则适合使用单调时钟，避免系统时间调整影响结果。

## 3. 为什么处理得越久，结果越旧

假设输入是每秒 25 帧，一次串行推理需要 100 毫秒，推理吞吐量只有每秒 10 帧。若每帧都排队，在其他条件不变的理想化情况下，每秒会多积压约 15 帧。

运行十秒后，队列增加约 150 帧。此时用户看到的框越来越滞后，并不一定是模型越来越慢，而可能是模型一直在处理越来越旧的输入。

对实时预览中的辅助检测，可以考虑“只保留尚未处理的最新一帧”：

```python
from threading import Condition

class LatestFrameSlot:
    """单消费者槽位；调用方负责 frame 的内存所有权。"""
    def __init__(self):
        self._cv = Condition()
        self._frame = None
        self._closed = False

    def publish(self, frame):
        with self._cv:
            if self._closed:
                return False
            self._frame = frame  # 替换未消费的旧帧
            self._cv.notify()
            return True

    def take(self):
        with self._cv:
            self._cv.wait_for(
                lambda: self._frame is not None or self._closed
            )
            if self._closed:
                return None
            frame = self._frame
            self._frame = None
            return frame

    def close(self):
        with self._cv:
            self._closed = True
            self._frame = None
            self._cv.notify_all()
```

这个槽位最多保留一个待处理帧，但它不能取消已经开始的推理，也不能保证端到端延迟必然达标。发布后，生产者还必须避免修改消费者正在读取的图像缓冲区；实际工程中需要明确复制、引用计数或缓冲池的归还规则。

这一策略也有边界：录像、短暂事件取证、需要连续帧的跟踪任务，不能直接照搬。此类需求要使用独立的数据路径，并为容量、丢失与过载制定明确策略。

## 4. 抽帧推理能省下哪些成本

“每五帧做一次检测”通常可以降低推理负载，但如果前面仍然解码了所有帧，解码开销并没有按相同比例下降。

对于采用帧间预测的视频，后续帧可能依赖前面的参考帧，因此也不能在压缩码流中任意删掉四帧，只留下第五帧交给解码器。

在多宫格场景，主子码流切换是一种更早介入资源分配的方法：小窗口使用较低分辨率码流，放大后再切换高质量码流。需要接受的代价是切流等待、解码状态重建，以及画面与识别坐标的重新对齐。

推理端则可以采用另一套频率：后台窗口低频采样，当前关注窗口提高频率。无论使用何种优先级，都应避免低优先级通道长期拿不到处理机会。

## 5. 让结果与画面对得上

识别结果只有一组矩形坐标是不够的。它至少需要关联到具体通道、连接会话与输入帧。

我会在结果接口中保留下面这些字段，数值仅作示例：

```json
{
  "stream_id": "camera-02",
  "session_id": "session-17",
  "frame_id": 1842,
  "source_size": [1920, 1080],
  "model_version": "detector-demo",
  "boxes": [[0.10, 0.20, 0.30, 0.60]]
}
```

这里假设框采用相对于原图的归一化坐标。若预处理包含裁剪、旋转或 letterbox，服务端需要先恢复到约定的原图坐标系，或者把变换信息一起交给前端。

会话标识尤其重要。重连之后，旧推理任务可能才执行完毕；即使 frame_id 相同，也不能把旧会话结果绘制到新连接上。界面应丢弃过期会话的结果，并根据任务需求决定是否允许有限时间差的叠框。

如果选择“框必须对应原帧”，就需要等待和缓存；如果选择“在最新画面上展示最近结果”，就要接受时间错位，并设定结果过期策略。这是产品语义和工程资源之间的取舍。

## 6. 用一组负载预算决定调度策略

假设四路输入各为 25 FPS，单个推理工作者每次处理一帧需要 100 毫秒，且暂不考虑批处理。总输入是 100 FPS，理论推理容量约为 10 FPS。增加到四个独立排队入口，不会把一个工作者变成四倍算力。

如果每路目标为 2 FPS，期望负载为 8 FPS，名义利用率是 80%。剩余空间用于吸收耗时波动，但这不是尾延迟保证；预处理、设备争用和突发输入都可能改变实际服务时间。

可以为每路保留最新待处理帧，再通过轮询选取通道。提高当前关注窗口的权重时，同时给后台通道设置最大等待预算，防止它们长期饥饿。

批处理可能提高吞吐，却增加等待凑批的时间。应同时限制批大小和等待期限，而不是只比较每秒处理帧数。若系统无法满足所有窗口的新鲜度预算，需要明确降级：降低分析频率、减少分辨率或减少并发通道。

## 7. 区分资源瓶颈与调度失控

我会先设计四组对照，而不是同时修改模型、码率和播放器参数：

1. **单路、仅预览**：建立解码与显示基线。
2. **多路、仅预览**：观察解码、内存带宽与渲染压力。
3. **多路、开启推理**：观察计算资源竞争和待处理队列。
4. **加入网络扰动与重连**：验证恢复时间、会话切换和旧任务清理。

每组固定输入、分辨率、码率和运行时长，记录帧率之外的队列等待、结果年龄与资源使用。这样才能区分“算不动”和“算得动但调度失控”。

RTSP 的传输方式也是对照项之一。FFmpeg 支持 RTSP over TCP 等方式，但选择 TCP 并不自动等于更低延迟；必须结合实际网络和缓冲行为测量。参数与协议选项应以 [FFmpeg 官方协议文档](https://ffmpeg.org/ffmpeg-protocols.html#rtsp) 为准。

回到最开始那个越来越滞后的框，我会先看它对应的帧什么时候进入队列，再看它属于哪个会话。前者能解释“为什么这么旧”，后者能解释“为什么它还出现在这里”。这两条信息比单独一个 FPS 数字更接近问题本身。

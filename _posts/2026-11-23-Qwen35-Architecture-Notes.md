我读 LLM 架构时，习惯先问两个问题：当前 token 从哪里取得信息，已经读过的内容又存在哪里。沿着这两个问题看，Attention、GQA、递归状态和 KV cache 才能连成一条计算路径。

Qwen3.5 9B 很适合用来梳理这件事。它保留了自回归生成的入口和出口，内部却交替使用两种序列建模方式，还接入了视觉输入。只记住“9B”“多模态”或“混合注意力”，仍然说不清一次推理到底做了什么。

这篇笔记先回到 Transformer 的基本计算，再对照 9B 的配置展开。配置核对于 2026 年 11 月 23 日；后面的缓存数字按给定假设推算，方便理解开销从哪里来。

## 1. 先沿着一个 token 走一遍

对于自回归语言模型，可以先画出下面这条主路径：

<pre class="architecture-flow"><code>输入文本 → tokenizer → token IDs → embedding
                                     ↓
                      多层序列建模模块与前馈网络
                                     ↓
                       最终归一化 → 词表 logits
                                     ↓
                          选择下一个 token
                                     ↓
                         更新历史，继续生成</code></pre>

假设输入是“这张图中的零件有几个孔”，tokenizer 将它变成一串整数，embedding 再将每个整数映射成向量。整数是词表索引，向量才是后续网络的计算对象；一个 token 也不必对应一个汉字或一个单词。

理解一层网络时，我会把它拆成两种运算。序列混合模块让当前位置读取其他位置的信息；前馈网络则对每个位置的特征做非线性变换。残差连接保留输入路径，归一化控制进入子模块的数值尺度。下面是常见 Pre-Norm 解码块的概念写法，不代表所有模型的精确实现：

$$
u = x + \operatorname{Mixer}(\operatorname{Norm}(x)),
\qquad
y = u + \operatorname{FFN}(\operatorname{Norm}(u)).
$$

标准注意力的核心是按相似度汇聚信息：

$$
\operatorname{Attention}(Q,K,V)
=\operatorname{softmax}\left(\frac{QK^\top}{\sqrt{d_k}}+M\right)V.
$$

其中，因果掩码 $M$ 阻止当前位置读取未来 token。这个公式来自 Transformer 的基本机制；原始 Transformer 还包含编码器，不能把它与现在常见的 decoder-only LLM 完全等同。[Transformer 原论文](https://arxiv.org/abs/1706.03762)

读新模型时，先问它替换了这里的哪个模块，比先背模型名称更有帮助。

## 2. Qwen3.5 混合了两种序列建模方式

Qwen3.5 的一个核心变化，是交替使用 Gated DeltaNet 和 Gated Attention。前者通过递归状态保存历史，后者保留全注意力路径。9B 属于 Dense 版本；系列中的 MoE 版本要另外看，不能因为家族介绍提到了专家路由，就认为 9B 的 FFN 也有专家选择。[Transformers 架构说明](https://huggingface.co/docs/transformers/model_doc/qwen3_5)

这里有两个相互独立的维度：

| 要回答的问题 | 关注的模块 | 典型选择 |
| --- | --- | --- |
| 不同位置之间怎样交换信息 | 序列混合模块 | 全注意力、递归状态、两者混合 |
| 每个位置怎样变换特征 | FFN | Dense、MoE |

因此，Dense 不等于“每层都是标准注意力”，混合注意力也不等于 MoE。把这两件事分开之后，架构图就容易读得多。

9B 的语言主干可以画成八组重复结构，每个方框内部还包括归一化与残差路径：

<pre class="architecture-flow"><code>token 表示
    ↓
┌──────────────────────────────────┐
│ Gated DeltaNet → FFN              │
│ Gated DeltaNet → FFN              │  × 8 组
│ Gated DeltaNet → FFN              │
│ Gated Attention → FFN             │
└──────────────────────────────────┘
    ↓
归一化 → 输出词表</code></pre>

也就是 24 个线性注意力层与 8 个全注意力层。官方模型卡给出了这一布局，并将模型定义为带视觉编码器的因果语言模型。[Qwen3.5-9B 模型卡](https://huggingface.co/Qwen/Qwen3.5-9B#model-overview)

我对这种布局的理解是：多数层负责持续更新历史表示，间隔出现的全注意力层负责直接访问此前位置。这是对设计取舍的解释，不能据此推导出某个任务必然更准确，也不能直接把层数比例换算成实际加速倍数。

## 3. Gated DeltaNet 到底在更新什么

全注意力可以保存历史位置的 K、V，再根据当前 query 读取。递归模型则维护一个状态矩阵 $S$，新 token 到来时更新这个矩阵。两者保存历史的方式不同。

把单个 head 的状态写成 $S_t\in\mathbb{R}^{d_v\times d_k}$，Gated Delta Rule 可以拆成三步：

$$
\widetilde S_t = \alpha_t S_{t-1},
$$

$$
S_t = \widetilde S_t
+ \beta_t\left(v_t-\widetilde S_t k_t\right)k_t^\top,
\qquad o_t = S_t q_t.
$$

先用 $\alpha_t$ 衰减旧状态，再比较“当前 value”与“旧状态在当前 key 上的预测”，最后写入差值。$\beta_t$ 控制这次更新的强度。这里展示的是论文的核心递推关系，省略了具体模型的投影、卷积、归一化与输出门控。[Gated Delta Networks](https://arxiv.org/html/2412.06464v3#S3.SS1)

可以用一个刻意简化的二维例子理解差值更新。设 $k=[1,0]^\top$、$v=[2,0]^\top$，初始 $S=0$，并暂时取 $\alpha=\beta=1$。第一次写入后，状态在这个 key 上返回 $[2,0]^\top$。第二次看到完全相同的 key-value，预测误差已经为零，因而不会再重复累加一次。这里取 1 是便于手算的边界情形，不是实际门控值的设定。

换成不正交的 key，更新可能影响其他关联。这也提醒我：固定形状的状态不是一份可以逐条无损读取的历史数据库。门控和更新规则让模型学会选择信息，但不会消除有限状态的表达约束。

“线性”描述的是在固定维度下，序列计算量随长度的增长关系，不表示网络没有非线性。训练时还可以按块并行计算，不能看到递推公式就认定训练只能逐 token 串行运行。

## 4. 读懂 9B 配置中的几个数字

下面只摘出与本文计算有关的字段。两类注意力的 head 参数要分别读取，不能混用。[官方 config.json](https://huggingface.co/Qwen/Qwen3.5-9B/blob/main/config.json)

| 配置项 | 9B 中的值 |
| --- | --- |
| 语言主干层数 / 隐藏维度 | 32 / 4096 |
| FFN 中间维度 | 12288 |
| 全注意力 Q heads / KV heads / head dim | 16 / 4 / 256 |
| 线性注意力 QK heads / V heads / head dim | 16 / 32 / 128 |
| 视觉编码器层数 / 隐藏维度 / 输出维度 | 27 / 1152 / 4096 |
| 配置中的最大位置数 | 262144 |

全注意力路径使用分组查询注意力，即多个 query head 共享一组 key、value head。GQA 要减少的是 KV 的保存与读取开销，并不把 query head 数一同降到 KV head 数。[GQA 原论文](https://arxiv.org/abs/2305.13245)

按表中的数值自行展开，在 batch 为 1、序列长度为 $T$ 时，全注意力路径的 Q 可以理解为 `[1, 16, T, 256]`，K、V 则各为 `[1, 4, T, 256]`。每组四个 query head 共享一组 KV。实际内核可以使用其他布局，这里只看逻辑形状。

这也是为什么估算 KV cache 时必须用 4，而不是 16。另一个容易混淆的地方是 256 和 128：它们来自不同模块，不能把线性层的 head dimension 填进全注意力的缓存公式。

## 5. 给 KV cache 算一笔账

设 batch size 为 $B$，全注意力层数为 $L$，已有 token 数为 $T$，KV head 数为 $H$，head dimension 为 $D$，每个缓存元素占 $s$ 字节。仅这一部分的理论存储量为：

$$
M_{\mathrm{KV}} = 2BLTHDs.
$$

开头的 2 对应 K 和 V。取 9B 的全注意力配置，假设缓存为 BF16、batch 为 1，每新增一个 token，需要：

$$
2\times 1\times 8\times 4\times 256\times 2
=32768\ \text{bytes} = 32\ \text{KiB}.
$$

因此，32768 个 token 对应约 1 GiB 的全注意力 KV cache。这个数来自上述假设，不包括线性层递归状态、卷积缓存、模型权重、视觉激活与运行时工作区，也没有计算缓存分页带来的额外空间。

对照之下，如果做一个假想实验，保持其他配置不变，把 32 层全部换成同规格全注意力，这一项就变成约 4 GiB。这只是帮助理解层数影响的估算，不是与另一个实际模型的性能比较。

推理还要区分两个阶段：

| 阶段 | 发生的计算 | 观察指标 |
| --- | --- | --- |
| Prefill | 处理输入序列并建立缓存或状态 | 首 token 延迟、输入吞吐 |
| Decode | 基于历史状态逐步生成 | 单步延迟、输出吞吐 |

混合结构降低了部分历史存储成本，但仍保留全注意力层。不能因此认为整个模型在任意长输入上都只有线性计算成本；也不能只凭缓存小，就判断首 token 一定更快。

## 6. 图像沿着另一条入口进入主干

Qwen3.5 支持文本、图像和视频输入。理解它时可以先把“感知输入”和“语言主干”分开：视觉内容先经过编码，再以与文本表示兼容的特征进入后续计算。[多模态架构说明](https://huggingface.co/docs/transformers/model_doc/qwen3_5)

<pre class="architecture-flow"><code>文本 → tokenizer → 文本 embedding ─────────┐
                                         ├→ 组织输入序列 → 混合主干 → 文本输出
图像 / 视频 → 视觉预处理 → 视觉编码与特征映射 ─┘</code></pre>

这个图省略了位置编码、特殊 token 和视觉 token 的排列规则。实际输入应交给模型配套的 processor；“能把两个 tensor 拼起来”和“符合模型训练时的输入协议”是两件事。

例如，给模型一张零件图，让它数孔，再追问左右两侧是否对称，信息至少经过三个环节：预处理有没有保留小孔，视觉表示有没有保留位置关系，语言输出有没有正确使用这些信息。回答出错时，只改最后的提示词可能找不到真正原因。

分辨率和视频帧数也会影响进入主干的视觉 token 数。因此，两条文本长度相同的请求，实际输入长度和开销可能差别很大。做记录时，我会同时保留图片尺寸、采样帧数和 processor 产生的输入统计，而不只记录文字字数。

## 7. 下一步怎样把阅读变成实验

读懂架构只是建立了可检查的假设。若继续做小规模实验，我会从下面几组对照开始，先固定模型版本、推理后端、精度、输出长度和采样参数。

| 想验证的问题 | 控制变量 | 记录什么 |
| --- | --- | --- |
| 长输入主要增加哪部分成本 | batch 固定，逐步增加输入长度 | Prefill 时间、Decode 时间、峰值显存 |
| 模型能否找回较远的信息 | 总长度固定，移动目标信息的位置 | 检索准确率、位置敏感性 |
| 小目标是否在预处理时丢失 | 同一图片，改变允许的输入分辨率 | 视觉 token 数、目标识别错误 |
| 并发如何影响服务表现 | 单请求长度固定，增加并发 | 等待时间、单请求延迟、总吞吐 |

这些实验能观察现象，但不会自动给出架构层面的因果结论。比如长文检索失败，可能与训练分布、提示方式或干扰信息有关，不能仅凭一次失败归因于递归状态。要比较两种架构的优劣，还需要更严格地匹配训练与推理条件。

对于 Agent 应用，也应把模型能力与执行系统分开测。模型可以生成正确的工具参数，但外部操作是否成功、超时后是否重复执行，仍由状态管理和工具协议决定。这部分可以接着看[让 Agent 从中断的地方继续执行]({% post_url 2026-11-23-Agent-Recoverable-Execution %})。

现在再看 Qwen3.5 9B，我会先检查层的排列与状态类型，再看各模块的维度，最后沿输入、缓存和输出核对实际开销。参数量只是其中一个数字，把这些路径连起来，才算开始读懂一个模型。
